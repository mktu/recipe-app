# セカンドオピニオン

実装した AI は、目の前のコードに集中するほど本来の目的から離れていく。
人のレビューの前に、**実装の文脈を持たない別の目**に見直してもらい、AI 同士で片付けられるものは片付ける。
PR 本文の濃淡（人が見る箇所と AI に任せる箇所）を、実装した AI の自己採点ではなく独立した目で裏付けるのが目的。

- **実装したセッションの中で、人が打つ。** 実装 AI は、答える側としてこのセッションの文脈を使ってよい
- **コストがかかるので自動では回さない。** 回すかどうかは人が決める
  （目安: Markdown 約 140 行の差分で、`/code-review low` と番人を合わせて subagent 約 9.5 万トークン）
- **これは指摘を受けて直す「レビュー」ではない。** 返ってくるのは問いで、従うかは実装 AI が決める

## 1. 準備

- 変更をすべてコミットして push する（WIP でよい）。どちらのレビューも、コミット済みのブランチ全体
  （`origin/develop` との差分）を見る
- 対象の PR と Issue 番号を確かめる。PR が無ければ、先に Draft PR を作る（`/work-issue` の 3-4）

  ```bash
  gh pr view --json number,url,body --jq '.number, .url'
  ```

  Issue 番号は、PR 本文の `Closes #<番号>` かブランチ名の末尾から取る。見つからなければ人に聞く

## 2. 2 つの目で見る

### バグ: `/code-review`

Skill ツールで `code-review` を呼ぶ。**強度とブランチ名を必ず引数で渡す**（例: `high feature/fix-xxx-123`）。
強度を省くと前回の強度が使い回され、対象を省くと未コミットの差分だけが対象になりうる。
強度は、このスキルの引数があればそれを使い、無ければ次で選ぶ。

| 差分 | 強度 |
|---|---|
| 小さい（数ファイル・挙動の変更が局所的） | `low` |
| 普通 | `medium` |
| 大きい／認証・データ（migration・RPC・削除）・LINE の返信に触れる | `high` |

### 目的の番人: `purpose-guardian`

「そもそも何をしたいんだっけ」の目線で見直す、読み取り専用の subagent（`.claude/agents/purpose-guardian.md`）。

- **番人は Bash を持たない**（Read / Grep / Glob だけ）。材料は呼び出し側が**コマンドで**ファイルに書き出して渡す。
  手で要約して書かない（実装中の判断の理由や PR 本文の下書きが混ざると、説得してしまい独立した目にならない）
  ```bash
  N=<Issue 番号>
  D=$(mktemp -d)
  gh issue view $N --json title,body --jq '"# " + .title + "\n\n" + .body' > $D/issue.md
  gh issue view $N --json comments --jq '.comments[] | select(.body | startswith("<!-- work-issue:decision -->")) | .body' > $D/decisions.md
  git fetch origin develop -q
  git diff origin/develop...HEAD --stat > $D/diff-stat.txt
  git diff origin/develop...HEAD > $D/diff.patch
  ```
- **渡すのは材料ディレクトリと作業ディレクトリの場所だけ。**
  ```
  Agent(subagent_type: "purpose-guardian",
        prompt: "材料ディレクトリ: <$D>\n作業ディレクトリ: <リポジトリのルート>\nこの変更を見直してください。")
  ```
- **`purpose-guardian` が見つからないとき**（agent の定義はセッション開始時に読まれるので、定義を足した・変えたセッションでは呼べない）:
  定義ファイルの frontmatter より下の本文を材料ディレクトリに書き出す。そのうえで `general-purpose` に
  「その本文を読んで従うこと・材料ディレクトリ・作業ディレクトリ・Bash を使わずファイルを変更しないこと」だけを渡して回す
  （`general-purpose` は Bash を持つので、ここは指示頼みになる）
- **省いてよいとき:** 目的が変更そのものと同じで、見失いようがない変更（ライブラリの更新、typo、原因が明らかな小さな不具合の修正）。
  省いたら、PR コメントにその理由を 1 行残す

`/code-review` と番人は並行して回してよい。

## 3. 答える（AI 同士で完結させる）

`/code-review` の指摘は直す。直さないと判断したものは理由を残す。

番人の問いには、1 つずつ次のどれかで答える。**正しさの一致は求めない**（番人の問いを盲目的に正しいとしない）。

- **対応した** — 何を変えたか
- **問題ない** — なぜ問題ないか（理由を必ず書く）
- **判断が要る** — 自分では決められない。**これだけを人に聞く**（選択肢と、自分ならどうするかを添える）

人に聞いたものは、答えをもらったら「対応した」か「問題ない」に直して記録する。
人がいない、または答えが出なかったものは「判断が要る」のまま残す（4 で PR 本文に載せる）。

対応して変更が大きくなったときだけ、もう一度番人に回す（**最大 1 回**）。
直したものはコミットして push する。

## 4. 結果を残す

### PR コメント 1 件

問いと答えを `gh pr comment` で **1 件**にまとめる。行ごとのコメント（`/code-review --comment` など）は使わない。

```markdown
<!-- second-opinion -->
## セカンドオピニオン

### `/code-review` <強度>
- （見つかったものと、どう直したか。直さなかったものは理由。無ければ「指摘なし」）

### 目的の番人
**番人が書いた目的:** （差分を読む前に番人が言葉にしたもの。1〜2 行）

1. **問い:** （番人の問い）
   **答え:** 対応した／問題ない／判断が要る — （何を変えたか／理由。人に聞いて決めたものは「人が判断:」と書く）
2. …

（省略した場合は「省略 — 理由」の 1 行）
```

### PR 本文

**問いと答えは本文に混ぜない。** 本文で変えるのは次の 2 点だけ（`gh pr edit --body-file`）。

- 「セカンドオピニオン:」の行を、どう回したかに書き換える
  （例: `セカンドオピニオン: /code-review medium、目的の番人（問い 4 件、判断が要る 1 件）`）
- 「判断が要る」のまま残った問いを、「最低限ここは見て」に 1 行ずつ足す
  （例: `【番人の問い】（問いの要約） — 判断が要る理由`）

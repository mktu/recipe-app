# Issue を進める（イシュー駆動開発）

Issue の状態は [recipe-app プロジェクト（#5）](https://github.com/users/mktu/projects/5) の **Status 列**で管理する（ラベルは使わない）。
このスキルは呼ばれたときに、その Issue の Status に応じて 1 段階進める。勝手に次の段階へは進まない。

| Status | 意味 | 誰が動かすか |
|---|---|---|
| `Todo` | 未整理（新しい Issue は自動でここに入る） | 自動 |
| `Plan` | 方針を詰めたい | 人 |
| `Needs input` | 人の番（論点への回答・判断） | AI |
| `Ready` | 方針について人と合意済み。着手待ち | AI（**人が合意したときだけ**） |
| `In Progress` | 実装してよい | 人 |
| `In review` | Draft PR が出ていて、人のレビュー待ち | AI |
| `Done` | 完了 | 人 |

**AI は `Ready` で止まる。`In Progress` に移すのは人。**

## 0. 道具

Status の読み書きは必ずスクリプトで行う（ID の取り回しを手でやらない）。

```bash
S=.claude/skills/work-issue/scripts/project-status.sh
$S get <番号>                 # Status を表示
$S set <番号> "<Status>"      # Status を変更
$S list "Plan" "Needs input"  # その Status の open な Issue 一覧
```

`project` スコープが無いと失敗する。そのときはユーザーに、普段のターミナルで
`gh auth refresh -h github.com -s project` を実行してもらう（Claude Code 経由では対話の認証ができない）。

### コメントの目印

gh は自分のアカウントで動くので、**AI のコメントも人のコメントも投稿者は同じ**になる。
AI のコメントは、1 行目に次のどれかの目印を必ず入れて区別する。目印より下の書き方は自由。

| 目印 | 用途 |
|---|---|
| `<!-- work-issue:question -->` | 論点・質問・考えの共有 |
| `<!-- work-issue:decision -->` | 合意した結論の記録（または、結論をどこに残したかへの案内） |
| `<!-- work-issue:blocked branch=<ブランチ名> -->` | 実装中に止まった |
| `<!-- work-issue:pr -->` | Draft PR を作った |

**最後のコメントに目印が無ければ、人が返信済み**と判定する。

```bash
gh issue view <番号> --json comments --jq '.comments[-1].body // ""' | head -1
```

## 1. 対象を決める

- **番号の指定あり**: `$S get <番号>` で Status を見て、下の分岐へ
- **番号の指定なし**: `$S list "Plan" "Needs input" "In Progress"` を表示して選んでもらう。
  `Needs input` は人が返信済みのものだけ示す（`In Progress` には手作業の Issue も入るので、勝手には拾わない）
- **「Plan の Issue をまとめて見て」**: `Plan` の Issue を順に 2 で処理する（**まとめ処理モード**）。
  まとめて処理するのは方針の検討だけ。実装はまとめて処理しない

| Status | すること |
|---|---|
| `Todo` | ユーザーがこのスキルで指定した ＝ 検討の依頼とみなし、`Plan` に移して 2 へ |
| `Plan` | 2（方針を詰める） |
| `Needs input` | 最新の目印が `blocked` なら 3（実装の再開）、それ以外は 2 の続き |
| `Ready` | 合意した方針を要約して「着手しますか？」と聞く。人が着手すると答えたら `In Progress` に移して 3 へ |
| `In Progress` | 3（実装）。合意した方針が見当たらなければ「先に方針を詰めますか？」と聞く |
| `In review` / `Done` | 何もしない。PR へのレビュー指摘に対応する場合は、指摘内容を伝えてもらって通常の作業として対応する |

## 2. 方針を詰める（Plan / Needs input）

**目的は計画書を書くことではない。人と対話して、不明瞭な点を無くすこと。**
Issue は雑に書かれている前提で読む。それを AI が理解する過程で、
書いた本人が知らなかった問題や、別の選択肢が見つかる。それを持ち出して議論し、より良い案を一緒に作るのがこの段階の価値。

### やること

1. **調べてから話す。** Issue 本文と全コメント、`docs/OPERATIONS.md`・`docs/ARCHITECTURE.md`・
   CLAUDE.md の「作業前に読む」表で該当する doc、関係するコードを読む。推測で論点を作らない
2. **理解を言い直す。** 「この Issue はこういうことをしたい、と理解した」を短く書き、ずれがあれば最初に正してもらう
3. **問題と選択肢を持ち出す。**
   - 書かれたとおりにやると困ること（既存の仕組みとの衝突、知られていない制約、docs にある落とし穴など）
   - 実現の仕方が複数あるなら、それぞれのトレードオフ。おすすめがあれば理由とともに言う。ただし決めつけない
   - 書かれていないが決める必要があること
4. **相談しながら案を作る。** 一度に全部を聞かず、大事な論点から進める。返事を受けて案を作り直す。
   折衷案を作ることも、途中で前提に戻ることもある。**方針が二転三転するのは正常なこと**で、早く結論を出すために議論を打ち切らない
5. **合意したら結論を残す。** 形は内容に合わせる（書式は決めない）。
   - 小さなものなら、`decision` コメントに結論を数行
   - 大きく変わったなら、人の了解を得て Issue 本文を書き換える／サブイシューに分ける
   - やらない・別の Issue にする、も結論になりうる
   - どこに残しても、`decision` コメントで「結論はどこにあるか」を 1 行示す（実装の段階でそれを読む）

### Status の移し方

- **`Ready` に移すのは、人が方針に合意したときだけ。** AI が「論点を書き終えた」「質問がなくなったと思う」という理由で移さない。
  移したら「着手するときは、ボードで `In Progress` に移すか、もう一度 `/work-issue <番号>` を実行してください（実行した場合は、着手してよいかを確認します）」と伝えて終わる
- 人が不在のとき（まとめ処理モード、バックグラウンド）は、調べた結果と論点を `question` コメントに書いて `Needs input` に移す。
  議論の続きは、人が返信してから次に呼ばれたときに行う
- 対話の途中で終わるときも、そこまでの議論で分かったことと残っている論点を `question` コメントに残し、`Needs input` にする

## 3. 実装（In Progress / blocked からの再開）

**目的は計画どおりに実装することではない。計画した人と、ユーザーの意図に沿った実装をすること。**
実装する AI は計画した AI と別のこともあるし、実装して初めて分かることもある。
方針と実態のズレを見つけて軌道を修正するのも、この段階の仕事。アウトプットは PR。

### 3-1. 準備
- Issue 本文と全コメントを読み、合意した方針を把握する（`decision` コメントが案内する場所を読む）。関係する doc も読む
- worktree を**必ず `origin/develop` 起点**で作り、`EnterWorktree` の `path` で入る
  （`EnterWorktree` で新規作成すると `origin/main` から切られる。CLAUDE.md「ブランチ戦略」）。
  ```bash
  git fetch origin
  git worktree add .claude/worktrees/<name> -b feature/<add|fix|refactor|docs>-<内容>-<Issue番号> origin/develop
  ```
  `blocked` からの再開なら、目印にあるブランチの worktree を使う
- **worktree には `node_modules` も `.env.local` も無い。** 入ったら、確認（3-3）の前に揃える。
  `.env.local` が無いと `npm run build` が Supabase の URL 未設定で落ちる（`docs/SUPABASE_LOCAL.md`）
  ```bash
  npm ci
  cp "$(git worktree list --porcelain | sed -n '1s/^worktree //p')/.env.local" .env.local  # メインのチェックアウトから
  ```

### 3-2. 実装する
進め方は臨機応変でよい。守るのは次の 1 点だけ。

- **方針と実態のズレを見つけたら、必ず会話する。** 方針が前提にしていたことが成り立たない、
  もっと良いやり方が見えた、意図の解釈が分かれる、など。黙って方針どおりに押し切らないし、黙って変えもしない
  - 対話中ならその場で相談する（2 に戻って方針を詰め直してよい）
  - 不在なら、WIP をコミットして push し、`blocked` コメント
    （何が分かったか／何を決めてほしいか。できれば選択肢つき）を Issue に付けて `Needs input` へ。
    PR ができる前に止まることもあるので、質問は常に Issue に書く
- 方針が触れていない細部（命名、文言など）は自分で決めてよい。気になるものだけ PR で伝える

### 3-3. 確認する
```bash
npm run lint && npm test && npm run build
```
`npm run test:e2e` はローカルで回さない（CLAUDE.md「E2E はローカルで常時回さない」）。Draft PR の CI に任せる。

差分を意図と突き合わせて読み直す（AI レビュー #255 と動作確認 #256 が入るまでは、この自己チェックだけ）。

### 3-4. PR で伝える（この段階の肝）

コミットして push し、**`--draft --base develop`** で PR を作る（base を省くと main に向く）。

**PR 本文が、この段階でいちばん大事なアウトプット。** 読み手は基本的にユーザー 1 人。

- **長い文章は読み飛ばされる。** 箇条書きで、1 項目 1〜2 行。説明文の段落を書かない
- **読む箇所に濃淡を付ける。** 「最低限ここは見て」を先頭に置き、3 件程度に絞る。全部を同じ重さで並べない
- **見るべき箇所が無ければ「なし」と書く。** 影響が極小で人が見るまでもない変更に、節を埋めるために項目を挙げない。
  節ごと消すと書き忘れと区別できないので、「なし」と理由を 1 行で書く（例: 文言の修正のみで挙動は変わらない）。
  「見なくてよい」と言い切ること自体が、読む手間を減らす情報になる
- **差分が大きいほど濃淡が大事。** 人の目で見るべき箇所と、AI レビュー（#255 で入る）に任せられる箇所、機械的な変更を分ける
- AI が確認したことと、人に確認を依頼することを、はっきり分ける
- 細かい記録（試したこと、コマンドの結果など）は `<details>` に畳む

```markdown
（何を・なぜ変えたか。3 行以内）

## 最低限ここは見て 👀
1. [`path/to/file.ts:42`](リンク) — なぜ見てほしいか（判断を置いた／方針から変えた／自信が低い）
2. 
（見るべき箇所が無ければ「なし — 理由」の 1 行だけにする）

## 動かして確かめてほしいこと
- [ ] （手順を具体的に。実機の LINE、iPhone の WebKit、staging など AI が確認できなかったもの）

## 方針から変えたこと
- （実装中に会話して決めたこと。無ければこの節ごと消す）

## 差分の見方
| 見る人 | ファイル |
|---|---|
| 👀 人 | 上の「最低限ここは見て」の箇所 |
| 🤖 AI レビューで足りる | （ロジックは素直で、テストで担保できているもの） |
| ⚙️ 機械的 | （型の追従、リネーム、生成物、テストの追加のみ など） |

（差分が小さいときは、この表を省いてよい）

<details><summary>AI が確認したこと ✅</summary>

- lint / test / build が通った
- （実際に確かめたことだけ書く。E2E の CI が緑でも、確認できている範囲は限られる: docs/OPERATIONS.md）

</details>

Closes #<番号>

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

`Closes #` は develop 向けの PR では発火しない（紐付けのために書く。Issue は main マージ後に手動で閉じる）。

最後に `pr` コメント（PR の URL）を Issue に付け、`In review` に移す。

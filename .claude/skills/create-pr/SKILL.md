# PR を作る

PR は、実装した AI から読み手への引き継ぎ。**読み手が「マージしてよいか」を判断するのにかかる手間を最小にする**のが目的。
書いた量や網羅性は価値にならない。以下は手順ではなく、読み手について分かっていること。これを満たすように書く。

## 読み手

- **基本的にユーザー 1 人。** Issue を立て、方針を合意した本人なので、Issue の背景や「なぜやるか」は知っている
- ただし**実装の会話は覚えていない前提**で書く。バックグラウンドで実装された、日をまたいだ、など
- GitHub の PR 画面で読む。「Files changed」タブで差分を上から読みながら判断する

## 読み手が欲しいもの

1. **自分が見るべき箇所と、なぜ見るべきか。** 判断を置いた・方針から変えた・自信が低い・壊すと影響が大きい、など。
   それ以外は見なくてよいと言い切ってもらえること
2. **自分にしかできない確認。** 実機の LINE、iPhone の WebKit、staging のデータなど、AI が確かめられなかったものを、具体的な手順で
3. **合意した方針から変わったこと。** 方針はすでに知っているので、知りたいのは差分だけ
4. AI が確かめたことの範囲（念のため見られる場所にあれば十分）

## 読みやすいと感じるもの

- **見てほしい箇所が、その行にインラインコメントで付いている。** 差分を読んでいる流れのまま、その場で理由が分かる。
  コメントには「なぜ見てほしいか」と「何を判断してほしいか」を書く（例: 「ここで空配列を null 扱いにした。既存の呼び出し元 2 箇所はどちらでも動くが、意図と合っているか」）
- **本文はインラインコメントへの入口として短い。** 何を・なぜを 3 行以内、インラインコメントが何件あるか、動かして確かめてほしいこと
- **「見るべき箇所なし」と言い切ってある。** 影響が極小なら「なし — 文言の修正のみで挙動は変わらない」の 1 行。
  見なくてよいと分かること自体が、読む手間を減らす。項目を埋めるためにインラインコメントを付けない
- **差分が大きいときは、ファイルを重さで分けてある。** 👀 人が見る／🤖 AI レビューで足りる／⚙️ 機械的（型の追従・リネーム・生成物など）
- **確認済みの細かい記録は `<details>` に畳んである。** 開かなくても判断できる

## 読みにくいと感じるもの

- **実装した内容を本文で説明し直す。** 何をどう変えたかは差分を見れば分かる。本文で読んでから差分でもう一度読むことになる
- **見てほしい箇所を本文に書く。** 本文 → ファイル → 該当行と追いかけるのが億劫で、結局読まれない。行が決まるならインラインに書く
- 段落の文章、経緯の物語、変更ファイルの列挙、全部を同じ重さで並べること
- 「方針から変えたこと」に、方針の範囲内で決めた実装の細部まで並べること
- AI が確かめたことと、人に確かめてほしいことが混ざっていること
- E2E の CI が緑であることを品質の根拠のように書くこと（実質ほとんど検証していない: `docs/OPERATIONS.md`）

## 決まり事と道具

- **base は必ず `develop`**（`gh pr create` の既定は main。過去に誤マージあり）。`/work-issue` から作るときは `--draft`
- タイトルは `feat:` / `fix:` / `refactor:` / `docs:` などで始め、Issue があれば末尾に `（Issue #XX）`
- 本文の末尾に `Closes #<番号>`（develop 向けでは発火しないが紐付けになる）と、Claude Code の署名行
- **`セカンドオピニオン: 未実施` の 1 行を本文に入れる。** 人が `/second-opinion` を打つとこの行が書き換わる
  （`.claude/skills/second-opinion/`）。本文から消すと書き換え先が無くなる
- **インラインコメントは、PR を作ったあとにレビュー 1 件としてまとめて付ける。** 自分の PR でも `COMMENT` のレビューは付けられる
  ```bash
  gh api repos/{owner}/{repo}/pulls/<番号>/reviews --input review.json
  ```
  ```json
  {"event": "COMMENT", "body": "", "comments": [
    {"path": "src/lib/foo.ts", "line": 42, "side": "RIGHT", "body": "…"},
    {"path": "src/lib/bar.ts", "start_line": 10, "line": 18, "side": "RIGHT", "body": "…"}
  ]}
  ```
  - `line` は変更後のファイルの行番号で、**差分（hunk）に含まれる行**しか指せない（外すと 422）。削除した行は `"side": "LEFT"` と変更前の行番号
  - 差分に現れない箇所（変えなかったことが論点、など）は、関係する変更行に付けるか、本文に書く
  - あとから push して行がずれると、コメントは outdated になる。見てほしい箇所が変わったら付け直す

# PR を作る

PR は、実装した AI から読み手への引き継ぎ。
読み手が「この PR をマージしてよいか」を判断するのを、どうすれば楽にできるかを考えて書いてほしい。
以下は読み手について分かっていること。どういう形にするかは、これを踏まえて PR ごとに決めてよい。

## 読み手について

読み手は基本的にユーザー 1 人。Issue を立て、方針に合意した本人なので、背景や「なぜやるか」は知っている。
一方で、実装中の会話は覚えていないことが多い（バックグラウンドで実装された、日をまたいだ、など）。

GitHub の PR 画面で、差分を上から読みながら判断している。

## 読み手が困っていること

- 本文に実装した内容が書き連ねてあると、本文で読んで差分でもう一度読むことになる。何をどう変えたかは差分を見れば分かる
- 「ここは見てほしい」が本文に書いてあると、本文 → ファイル → 該当行と追いかけるのが億劫で、結局追わない。
  差分を読んでいる流れの中、その場で目に入れば読める
- 長い文章や、全部が同じ重さで並んでいるものは、読み飛ばしてしまう
- AI が確かめたことと自分が確かめるべきことが混ざっていると、自分は何をすればいいのかが分からない

## 読み手がありがたかったこと

- 見る箇所に濃淡が付いていること。差分が大きいときは特に、人が見るところ・AI に任せてよいところ・機械的なところが分かると助かった
- 「見なくてよい」と言い切ってもらえること。それ自体が読む手間を減らす
- 実機の LINE や iPhone など、自分にしかできない確認が、すぐ試せる形で挙げてあること
- 合意した方針から変わったこと。方針はもう知っているので、知りたいのはそこからの差分

## 知っておくと事故を避けられること

- `gh pr create` の既定の base は main。この repo の PR は develop 向けで、過去に main へ誤マージしたことがある（PR #95）
- `Closes #NNN` は develop 向けの PR では発火しないが、Issue との紐付けにはなる
- E2E の CI が緑でも、実質ほとんど何も検証していない（`docs/OPERATIONS.md`）
- タイトルはこれまで `feat:` / `fix:` / `docs:` などで始め、Issue があれば末尾に `（Issue #XX）` を付けてきた
- 差分の行へのコメントは、レビュー（`event: COMMENT`）として付けられる。自分の PR でも付けられる
  ```bash
  gh api repos/{owner}/{repo}/pulls/<番号>/reviews --input review.json
  ```
  ```json
  {"event": "COMMENT", "body": "", "comments": [
    {"path": "src/lib/foo.ts", "line": 42, "side": "RIGHT", "body": "…"},
    {"path": "src/lib/bar.ts", "start_line": 10, "line": 18, "side": "RIGHT", "body": "…"}
  ]}
  ```
  - `line` は変更後のファイルの行番号で、差分（hunk）に含まれる行しか指せない（外すと 422）。削除した行は `"side": "LEFT"` と変更前の行番号
  - あとから push して行がずれると、コメントは outdated として畳まれる
